## 4分類

| 分類 | 対象の例 | 判断と扱い |
|---|---|---|
| ① 触らない公開資産 | HTML、写真/サムネイル、CSS、ロゴ、会報本文、辞書ダウンロード、過去行事 | 既存pathを保全。古い年・形式・タイポだけで削除/変換しない |
| ② 非公開管理へ分ける候補 | 編集用Office原稿、作業用コピー、退避ZIP、バックアップ | サーバーに存在するかは未確認。担当/由来/公開用途を確認後、公開root外または別の私有保管場所への移管を別途承認する。ローカル原本や証拠は既に公開stage外 |
| ③ 同一hash重複 | 同じ画像の別pathコピー | 全バイト比較と参照関係を確認する。同一内容でもURL別名に用途があれば両方維持。管理上の一本化を先に行い、公開コピーは無理に消さない |
| ④ 参照なし・用途不明 | 内部リンクから到達できないHTML、拡張子不明、`.bak`/`old`等の名称 | 未使用とは判定しない。所有者・履歴・外部直リンク・必要なら本人提供アクセス記録を確認するまで保留 |

## 段階的な進め方

1. **増やさない整理**: 新規記事だけ共通bundleと記事専用画像フォルダに統一。バックアップ/原稿を公開stageへ入れない。既存ファイルは触らない。
2. **現状の読み取り専用棚卸し**: 完全mirrorが手元にないため必要。本人起動の既存publisherへ別の明示的な「一覧だけ取得」モードを追加する案を、整理実施前に準備する。対象rootを `/home/ippon/www` に固定し、MLSDのpath/type/size/modifyと取得日時を記録。symlinkを辿らず、範囲・深さ・件数を制限し、拒否/中断を「空」と扱わない。STOR/MKD/DELE/RNFR/RNTO/権限変更を持たせない。資格情報は本人起動処理内のみ。現時点ではこのモードの実装・実行はしていない。
3. **候補だけ内容確認**: 一覧から候補を絞り、本人が必要範囲を読み取り保存してSHA256を算出。HTMLのhref/src、CSSのurl、フレーム、画像ページ、ダウンロードを対象に参照表を作る。内部参照ゼロと外部参照ゼロを区別する。全サーバーの秘密やメール領域を探索しない。
4. **候補単位の承認**: 各pathについて担当者、由来、参照元、外部直リンク確認、履歴、保存先、復旧ファイルのhashを揃える。「削除可」ではなく「残す/私有保管へ移す案/保留」を提示し、移動・削除・権限変更は本人の別承認後に限る。
5. **事前バックアップと小分け実施**: 承認対象の原バイト・path・時刻・hash・既存権限を保存し、復元可能性を先に検証。最初は数件だけ。公開URLの変更は避け、移管が必要でも旧URLが参照されていればその資産を残す。新しい公開backupsフォルダを作らない。
6. **検証と復元**: 変更前後の主要導線・対象URL・画像/ダウンロード・文字コードを照合。無関係ファイルの差分ゼロを確認。問題時は同じpathへバックアップ原バイトを復元してhash/HTTPSを再確認する。復元も本人が承認した操作として実施し、未知の上書きがあれば停止する。

整理の完了条件は「ファイル数が減った」ではなく、管理対象と持ち主が分かり、公開URLが維持され、再更新と復元が確実になったこと。現時点の未確認はサーバー全一覧、非公開原稿の実在、外部直リンク、担当者/所有者、全体バックアップの鮮度。これらがない状態で削除対象は確定しない。
